# CAG-Grounded Validation Report

**TRINETRA — MPLADS Risk Intelligence & Investigation Platform**
Report version: `cag-validation-1` · Generated by: `backend/app/services/validation/cag_validation.py`

## 1. Purpose

Demonstrate whether TRINETRA's existing detection engine can identify the
irregularity **patterns** documented in real CAG audit findings related to
MPLADS.

The claim being tested is deliberately narrow:

```text
Real CAG finding/pattern
   ↓
Abstract the irregularity pattern
   ↓
Map it to TRINETRA's detection capability
   ↓
Run a controlled representative/synthetic reproduction
   ↓
Report whether TRINETRA's logic is capable of flagging that pattern
```

This is **capability validation**. It is NOT a claim that "TRINETRA detected a
real CAG case." The three layers are kept strictly separate throughout:

1. **Real CAG evidence** — verified findings, quoted with report numbers and
   paragraph references (Section 3).
2. **TRINETRA's interpretation/mapping** — which detector targets the pattern
   (Section 5, catalog in `app/data/cag_catalog.py`).
3. **Synthetic reproduction** — controlled fixture rows carrying only the
   structural signature of each pattern (`app/data/fixtures/cag_patterns.csv`).

## 2. Data limitations

- TRINETRA has **no access to the underlying real work-level MPLADS records**
  audited by the CAG. Work-level analytical fields are not published on the
  e-SAKSHI dashboard (see docs/MEMORY.md, "Official Source Reality").
- Consequently **no accuracy, precision or recall metrics against real CAG
  data are claimed anywhere in this report**. The question answered here is
  only: "can the detector fire on the documented pattern's structure?"
- Fixture provenance is explicit and machine-checked: every fixture work ID
  is `CAGV-`-prefixed, the dataset is ingested with `is_synthetic=True`,
  and its source label carries the marker `synthetic_cag_pattern`.
- The fixture statement, stamped on the dataset and repeated in every API
  response:

  > "This fixture reproduces the structural characteristics of documented
  > CAG irregularity patterns for detector validation. It is not the
  > original CAG dataset, contains no real MPLADS records, and demonstrates
  > detection capability only — it does not claim that TRINETRA detected any
  > real CAG case."

- Detection thresholds were **not modified** to force positive results: the
  fixture was tuned so the baseline rows stay quiet while the pattern rows
  carry only the documented signature. Seven of eleven baseline rows emit
  no signals at all; four remain mildly active (score ≤ 6.0, HIGH or
  below) and are listed in Section 9.

## 5. Validation methodology

1. `run_cag_validation()` ingests `cag_patterns.csv` through the **unmodified
   official ingestion pipeline** (schema detection, normalization, validation,
   provenance).
2. The dataset is stamped `is_synthetic=True`,
   `version=cag-validation-1`, source label
   `synthetic_cag_pattern: …`.
3. The **unmodified detection pipeline** runs exactly as in production
   (quality → metrics → peer benchmarking → rules → compliance → agency
   concentration → NLP duplicates → Isolation Forest → fusion), pinned to a
   deterministic reference date.
4. For each pattern, the service checks whether the mapped detector emitted
   its expected signal on the fixture work(s), captures the fused priority,
   and reports one of:
   - `FLAGGED` — expected signal fired.
   - `PARTIAL` — expected signal did not fire but other independent signals
     converged on the work.
   - `MISSED` — no signal converged (reported honestly).
   - `NOT_VALIDATABLE` — pattern requires data TRINETRA does not have; never
     faked.
5. A `queue_entry_check` records whether each fixture work would enter the
   investigation queue (fused priority MEDIUM or above).

## 7. Machine-readable artifact

`GET /api/v1/validation/cag` returns the full report (sources, quotes,
per-pattern results with signal/evidence detail, queue-entry checks,
disclaimer). `GET /api/v1/validation/cag/summary` returns the compact table
the Evidence & Validation screen renders. Both carry
`meta.is_synthetic = true`.

## 8. Failed/partial detections

No mapped detector missed its pattern in the reference run. The honest
failures are the three **NOT_VALIDATABLE** patterns (002, 005, 009): these
require data (recommendation/sanction trails, authority fund ledgers,
records-keeping registers) that work-level exports do not carry. They are
documented as detection gaps, not patched over.

## 9. Limitations

1. **No accuracy claims.** Without the CAG's underlying work-level records,
   precision/recall against real cases is unknowable. This report
   demonstrates capability on structural reproductions only.
2. **Signature ≠ root cause.** E.g. PATTERN-006 is flagged through its
   statistical spend-vs-progress profile; the audit established the scope
   changes from documents TRINETRA does not hold.
3. **Fixture baselines are not perfectly quiet.** CAGV-BASE-01 (HIGH, 6.0),
   BASE-05 (HIGH, 4.5), BASE-06 (HIGH, 4.5) trigger cost/delay signals
   because they share a district with the pattern rows; the remaining seven
   baselines emit nothing. Thresholds were left untouched.
4. **Compliance matching is textual.** The CAG verified work nature on the
   ground; TRINETRA matches description text against guideline categories.
5. **The 2010 report chapters are scanned PDFs**; findings are cited from
   the report's published Executive Summary and the report page on
   cag.gov.in rather than page-level quotes (except where a text-layer PDF
   exists, as for Report 22 of 2025 Para 3.1).

## 10. What would require real work-level data

- Measuring real precision/false-positive rates per detector.
- Reproducing the actual cases behind CAG paragraph references.
- Detecting PATTERN-002 (missing MP recommendations) and PATTERN-005
  (authority-level utilization) — both need official data that is not
  publicly exported today.
- Validating duplicate detection against confirmed duplicate pairs.
